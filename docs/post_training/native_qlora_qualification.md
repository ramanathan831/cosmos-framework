# Native QLoRA qualification checklist

**The native QLoRA path is implemented and experimentally measured, but it is not release-qualified.** The existing trained NF4 model's supervised-token NLL was 4.18% higher than the matched BF16 control on the exposed WTS diagnostic, exceeding the unchanged 2% margin. A subsequent data audit also found related recording families across the original training and validation splits. Neither faster preprocessing nor new configuration acceptance resolves these quality requirements.

This checklist reviews implementation commit `55e7f14dfeca84002d0324108808a0e682579842`. Historical full-training evidence belongs to the earlier sealed `c5b8d49` and `a406ea1` runtimes. The [continuation kernel gate](evidence/native_qlora_kernel_gate_55e7f14.json) passed all 14 CUDA cases and the existing higher-precision native CPU regression for the exact `55e7f14` wheel, without skips. New workload settings and development experiments still require their own completion receipts; historical evidence does not automatically qualify a new build. See the [native training guide](native_qlora.md), [original design](qlora_native_vlm_design.md), and [qualification tool instructions](../../tools/native_qlora_qualification/README.md).

The [continuation audit evidence](evidence/native_qlora_qualification_audit_20261030.json) records the four-arm reanalysis, per-example differences and uncertainty, source metadata and split audit, sealed experiment criteria, and completed CPU workload shapes. It does not claim completion of the new GPU runs.

The [new build-preservation check](evidence/native_qlora_cross_build_55e7f14.json) reproduced the archived four-update NF4 and BF16 states from fresh training with the original inputs. Adapter and optimizer payloads, trainer state and data cursor were byte-identical. DCP index serialization differed, while decoded entries matched; model metadata differed only in the two declared code/wheel identity fields. This qualifies the timing counters for that diagnostic trajectory. It does not establish a new 300-update result or permit cross-build production resume.

The native lifecycle does not call `prepare_model_for_kbit_training`; it owns freezing, dtype policy, initialization and activation-checkpointing directly. Frozen embeddings need not become trainable to propagate gradients through adapter-bearing blocks. Blanket model dtype/device conversion is not part of the quantized lifecycle. A sharded extension must first define quantized parameter/metadata layout, storage dtype, frozen/trainable wrapping boundaries, all-gather and device-movement behavior, optimizer construction, save/load and topology restrictions for the actual native distributed stack. An upstream FSDP example does not qualify that extension.

## Reload, resume and export checklist

- [x] Historical fresh-process DCP and portable reloads reproduced controlled text, image and video logits/losses with `atol=0, rtol=0` on the same effective base.
- [x] Historical four-update canaries resumed from a completed update and matched adapter/optimizer tensors, RNG, cursor and controls exactly. These are not 300-update interruption experiments.
- [ ] Run the continuation's [lifecycle checks](../../tools/native_qlora_qualification/lifecycle.py#L218) for each selected numerical configuration, including process loss after a real accumulating microbatch. Saving partial accumulation must be refused; recovery starts from that attempt's last committed boundary.
- [ ] Keep exact resume identity checks for build, base, processor, strategy, execution settings and training contract. Portable reload can omit the original schedule/data contract, but must preserve the exact base/revision, quantizer/dependency versions and settings, resolved adapter targets/configuration, processor/tokenizer/template and model-format identity. Additional trained modules are rejected on this initial path.
- [ ] Reject incomplete checkpoint components, incompatible identities and unexpected tensor inventories before accepting recovery.

In idealized weight notation, training uses `dequantize(Q(W)) + ΔW`. Applying the same adapter to the original BF16 `W` instead yields `W + ΔW`, a different numerical model. Exporting dequantized quantized weights plus the adapter is also subject to arithmetic/rounding changes, and subsequent requantization changes the model again. None of these operations inherits the same-quantized-base reload result. Universal in-place four-bit merging and serving-backend compatibility are not promised.

## Quality findings and data separation

The original 256-row diagnostic is now an exposed regression set. It must not select new settings. Its completed trained scores remain NF4 **229/256**, native token NLL **0.1535318087305768**, versus BF16 **230/256**, NLL **0.14737239200007934**. These are teacher-forced environment-VQA measurements using each question's actual two, three or four answer choices and the native answer/end-token mask, not free-generation accuracy. The [archived evidence](evidence/native_qlora_wts_pipeline_a406ea1.json) remains unchanged.

Recomputing the four archived score files shows that the [trained loss difference is concentrated in answer-letter probabilities](evidence/native_qlora_token_contributions_20261030.json): full-vocabulary answer NLL increases by 4.184%, and restricted-choice NLL by 4.209%. The answer contribution to the native mean-token gap is approximately `0.00616551`, versus a total gap of `0.00615942`; the other-token residual, including numerical roundoff, offsets it slightly. This is not a separately measured exact end-token loss or evidence of a causal coding defect. Frozen NF4 also has lower NLL but lower accuracy than frozen BF16, illustrating why the two metrics need not move together. All rows and the original failed 2% gate remain unchanged.

A conservative audit groups all trials/cameras/events sharing a dated recording prefix and joins exact media hashes transitively. Seven recording families span the original train/validation boundary: 360 training rows and 305 validation rows; 27 of the scored 256 rows belong to those families. Exact video-byte disjointness therefore did not establish related-recording independence. The grouping policy is implemented in [common.py:51](../../tools/native_qlora_qualification/common.py#L51) and [split.py:27](../../tools/native_qlora_qualification/split.py#L27).

Original annotation metadata confirms that all 8,231 rows are `type=environment`, `phase=full_video`. Its 157 distinct `wts_id` values add no links across the conservative recording components. This does not qualify trajectory/action reasoning or prove that different recordings contain independent actors/events.

The old 256 scores, first 64 validation rows and all 16 original canary IDs expose 51 of 52 validation recording families. Only **32 rows in one training-disjoint, unexposed family** remain. One cluster cannot estimate independent-cluster uncertainty. A different pathname for the same source data does not create an untouched final set.

[Reconstructing the historical native cursor](evidence/native_qlora_historical_training_exposure_20261030.json) from the exact training bytes, seed 42 and 300 updates confirms that its first 2,400 examples covered all 96 original training recording groups. The cursor source is byte-identical to the sealed historical runtime. Unconsumed sibling clips in those groups therefore do not provide additional independent untouched groups.

The original design does not impose a universal training-speed improvement. Historical cache/prefetch timing and its 42.7% within-NF4 reduction remain separately scoped in the [performance report](evidence/native_qlora_performance_a406ea1.json). New NF4-versus-BF16 timing must use matched sequential allocations, counterbalanced order and recorded GPU identity, eight physical CPU cores/affinity/NUMA placement, runtime, processor and workload settings. Three paired trials give limited uncertainty evidence; profiler traces are diagnostic and excluded from throughput estimates.

Report loading and first-update peaks separately from steady updates, validation, checkpoint writes, portable publication, reload probes and scoring. Native `timer/e2e_step_s` excludes validation/checkpoint boundaries; complete experiment elapsed time includes all stages and their orchestration/verification costs. External sampling begins after disposable preflight, which is wall-timed separately. Retain per-update timings for updates 1–300, 6–30 and 31–300, and calculate examples/s and valid tokens/s from total counts divided by elapsed time.

Allocator peaks end at their named boundary after the preceding reset: `checkpoint_begin` reports the prior interval, while `checkpoint_complete` after it reports checkpoint writing. Reject invalid NVML sentinels/ownership/identity before interpreting a memory comparison. Report sampling gaps, owned-process versus whole-device memory, RSS/PSS completeness and host peaks. A cache-byte limit bounds retained entries, not decoder buffers, worker heaps or total host residency.

The current sampler records owned descendant RSS/PSS; unmapped filesystem page cache is outside that measurement, and short-lived or reparented processes can escape a sample. Native `VmHWM` is a rank's lifetime high-water mark, not a phase-specific process-tree peak. Checkpoint logs additionally record rounded cgroup usage at selected boundaries. Their innermost-cgroup `unlimited` label does not rule out an ancestor limit. Retained Slurm step RSS/VMSize/TRES accounting is supplemental evidence; virtual address space and scheduler samples must not be reported as peak total physical host residency. Complete host residency, including page-cache charges and ancestor constraints, remains a measurement limitation.

Preprocessing counters in the last training frame include initial and earlier validation, but exclude final validation performed after that frame. Processing calls include cache hits; they are not decoder-call counts. Processing and waiting overlap execution and must not be summed into wall time. The CPU replays below contain no model or concurrent GPU training.

The [completed CPU thread-policy comparison](evidence/native_qlora_worker_threads_20261030.json) processed 1,000 real WTS rows per arm in two counterbalanced repeats with a 1 GiB cache. Limiting BLAS threads changed worker thread count from 23 to two, but peak PSS differences changed direction: approximately 0.110 GB more in one repeat and 0.304 GB less in the other. That intervention does not establish a reliable residency fix. End-only trim released freed allocator pages with the live cache preserved, motivating a separate paired experiment.

The [completed periodic-reclamation diagnostic](evidence/native_qlora_worker_memory_20261030.json) kept inherited thread settings and compared worker-local `malloc_trim(0)` every 128 completed rows against matched sham verification at the same drained boundaries. Two clean opposite-order pairs processed 1,000 rows per arm on eight physical cores with sixteen allowed hardware threads. Affinity and environment matched within each pair; all four processed tensor records, row order, data cursor and parent RNG matched exactly. Every intervention preserved live-cache tensors, counters and worker RNG, with no explicit GC or eviction. Fresh workers' initial RNG states differed, so preservation is claimed within each worker, not across initial states.

Periodic trim reduced these sampled boundary peaks by approximately 1.08 and 1.11 GiB, but the trim arms were slower by about 12 and 210 seconds. Order, warm caches and system load remain confounded; no speed improvement is established. The 14 trim calls themselves totaled about 0.353 seconds, which excludes deferred page faults and end-to-end training costs. The initial failed sham completed row processing but exceeded its whole-child timeout after result publication; its evidence is retained and excluded from paired effects. A separately sealed rerun completed cleanly with a longer timeout and post-result shutdown timestamps.

These results support reclaimable allocator residency in the instrumented CPU replay. They do not identify a leaking object, establish a universal host-memory bound or qualify a production reclamation policy, larger-media workload or training-memory benefit. The [public diagnostic](../../tools/native_qlora_qualification/README.md#runtime-and-memory-diagnostics) exposes periodic sham/trim only through an explicit option and preserves the earlier end-only defaults. No production allocator change was made, and these host measurements do not satisfy the separate device-memory release gate.
